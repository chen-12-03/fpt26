# HLS 优化 Agent 后续优化方向及应用创新点报告

结合前期的文献检索和现有测试结果，我对作品下一步可以继续完善的方向做了一次整理。目前 Agent 已经有比较完整的验证和回退流程，能够判断一个修改是否通过 C 仿真、综合、频率、资源等门控。现阶段更需要解决的问题，是怎样让 Agent 不仅会判断方案能不能用，还能更稳定地提出真正有效的优化方案。

## 相关方向与当前判断

这次检索中，我认为和当前作品联系比较紧密的主要是 A、C、E、F 四个方向。

1. **方向 A：对修改过程增加更严格的正确性验证。** 当前系统主要依靠 CSim、Synth 和 CoSim 判断候选是否可用，这种方式比较适合现有作品，但仍然受测试输入覆盖范围的限制。后续可以先选择循环展开、循环重构、归约和局部缓存等几类常见修改，为它们补充适用条件和局部等价性检查。这样不需要一开始就解决任意 HLS 程序的完整形式验证问题，实施难度相对可控。

2. **方向 C：在有限预算内安排优化和验证流程。** 当前系统已经有积分和轮数限制，但每个候选基本还是按照固定流程进行验证。后续可以让 Agent 根据剩余预算、候选的预期收益和判断把握，决定是否值得继续综合，或者是否需要使用成本更高的验证工具。不过，这个方向更适合在候选质量有所提高后开展，否则只能减少无效尝试，不能直接提高优化能力。

3. **方向 E：让历史经验带上适用条件。** 现有 QoR-RAG 已经能够检索规则以及成功、失败案例，但目前仍比较依赖关键词和人工规则。后续可以把经验记录得更具体，包括当时的循环和数组结构、综合瓶颈、采用的修改、性能和资源变化，以及该经验在哪些器件和工具版本下有效。如果新任务与历史案例差异较大，或者相似案例的结果互相矛盾，Agent 应当放弃使用这条经验，避免出现负迁移。

4. **方向 F：在优化中保留安全和可靠性要求。** 这个方向主要面向密码核、汽车、航天和医疗控制等场景，要求性能优化不能破坏掩码、冗余、故障检测等机制。它的应用价值比较明确，但需要专门的安全测试或硬件测量条件，暂时不适合作为当前作品的第一优先级。此前考虑的“记录每次修改并定位失败来源”，更接近 A 和 E 中的修改追溯，可以先在现有系统中实现。

综合当前作品的基础，我更倾向于先参考 A 和 E：一方面把每次修改拆得更清楚，方便验证和回退；另一方面让历史经验带上使用条件，减少同一种优化方法被不恰当地套用到不同任务上的情况。

## 当前 Agent 的主要局限

现在的 Agent 并不是完全不能优化，它更擅长判断一个候选能不能保留，但还不太擅长主动找到更好的方案。例如，综合报告提示 II 受限时，Agent 有时会直接尝试加入 `PIPELINE`，却不能稳定判断问题到底来自存储端口、循环依赖、运算符延迟还是时序压力。即使系统能够正确拒绝这次修改，也不一定能进一步提出合适的替代方案。

因此，我认为当前主要问题不是门控或评分不够严格，而是从“发现综合报告中的问题”到“选择对应的硬件优化动作”之间还缺少一层更细的分析。继续增加测试任务仍然有必要，但如果这些结果不能进一步转化为可复用的诊断和修改经验，单纯扩大测试量对优化能力的帮助会比较有限。

## 后续优化计划及应用场景

目前考虑的整体路线是：

> **硬件瓶颈分析 → 拆分优化动作 → 记录实际效果 → 完善经验复用 → 加入局部验证和预算安排**

1. **先整理常见硬件瓶颈。** 重点区分存储端口、循环依赖、时序、资源和数据流等问题，并整理每类问题可能采用的修改、不能采用的修改以及预期看到的综合结果。对于没有明显优化空间的设计，也应尽早停止，避免反复调用工具。

2. **把每次修改拆成相对独立的动作。** LLM 主要负责分析问题、选择目标和规划修改，常见 pragma 可以由固定程序完成。每个候选尽量只包含一个主要动作，并记录它对 latency、II、clock 和各类资源的实际影响。这样在门控失败时更容易判断是哪次修改造成的问题，也方便后续回退和复用。

3. **在现有 QoR-RAG 上完善经验使用条件。** 检索历史经验时，先比较循环结构、数组访问、资源余量、器件和工具版本，再决定是否采用。如果证据不足就不强行迁移。等这部分比较稳定后，再为少量常见代码重构加入局部等价性检查，并尝试根据候选价值动态分配综合和验证预算。

4. **结合实际优化效果逐步选择具体应用领域。** 领域聚焦应建立在 Agent 已具备基本瓶颈分析和优化能力的基础上，同时也可以利用同一领域中较稳定的程序结构和约束，进一步缩小优化动作范围。具体实施时，可以从多个公开工程中选取一部分作为领域开发集和经验库，用于整理和积累优化规律；另外保留来源独立的工程作为测试集，检验这些经验能否迁移到未见任务，避免同一项目的相似代码同时出现在经验库和测试集中。

领域选择应主要考虑公开工程数量、实验复现条件、评价指标是否明确以及 Agent 的实际优化效果。AI FPGA 有 `hls4ml` 等成熟工具，比较容易构建应用展示，但相关研究较多；生物信息动态规划具有较清晰的存储复用和数据流结构，可以借助 DP-HLS 形成更有区分度的应用案例。医疗安全控制可作为远期方向，待具备可靠性标准和相应实验条件后，再进一步考虑方向 F。

现阶段我准备先完成硬件瓶颈分类和优化动作拆分，再利用现有任务结果完善经验记录方式。这样既能直接针对当前优化能力不足的问题，也能保留作品现有验证和回退机制的优势。在此基础上，再根据领域任务上的实际效果确定后续重点应用方向，并决定是否加入更严格的形式验证或预算调度。

上述第一阶段已完成一次真实日志驱动的实现与小样本验证，详见
[HLS 硬件瓶颈诊断实施与验收报告](HLS硬件瓶颈诊断实施与验收报告.md)。该实现没有让
LLM 直接猜测日志类型，而是先由确定性程序提取工具证据，再让 LLM 在证据范围内解释、
选择动作，并根据后续 CSim、Synth、必要 CoSim 和 Q_HW 结果修正路线。
